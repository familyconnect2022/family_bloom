1) SCOPE IMPLEMENTED
- Additive realtime 1v1 Chess domain only.
- Mobile: Chess Lobby, member presence overlay, challenge/cancel/accept/reject, realtime board, legal hints, promotion, clocks, draw/resign/rematch, reconnect/resync, bounded history.
- Backend: Node.js + Express + Socket.IO + chess.js + Firebase Admin SDK.
- Firebase remains Spark. Firestore is durable persistence/history only, never Socket transport/timer heartbeat.
- Existing Auth/Profile/Family membership/Family Graph/Moments/Events/Calendar/media/notifications and six Nhà Mình games are not migrated.

2) AUTHORITY / SECURITY
- Firebase ID token is taken from the authenticated mobile user and sent in Socket.IO auth handshake.
- Render verifies token using Firebase Admin verifyIdToken().
- Server never trusts client UID, role, color, turn, winner, FEN, PGN, remaining time or game-over claims.
- Server validates family membership on lobby/game entry and re-validates membership for gameplay mutations using a 10-second bounded cache.
- Runtime Socket payloads validate family/game/invite IDs, requestId, revision, chess squares, promotion and the exact supported time-control set.
- Game room join is accepted only for one of the game players.
- Client write to chessGames and chessActiveUsers is denied by Firestore Rules.
- Firebase Admin credentials are environment-only; no secret is committed.

3) SERVER-AUTHORITATIVE CLOCK / RECOVERY
- Runtime elapsed time uses performance.now() (monotonic).
- One shared 300ms timeout scheduler covers active games; no setInterval per game and no 1-second Firestore write.
- Timeout eligibility is re-checked after entering the per-game mutation queue, preventing a stale deadline task from flagging the wrong player after a move changed the turn.
- A move received after the authoritative deadline first persists/broadcasts the timeout result; the late move is not applied.
- Player-only disconnect does not pause a timed game.
- Process/server restore of persisted active state changes game to paused first; persisted remaining times are preserved so unprovable infrastructure downtime is not charged.
- Both players must reconnect before a recovered game resumes.
- Client countdown is display only and uses performance.now() from the latest authoritative state receipt.

4) DURABILITY / IDEMPOTENCY
- Per-game mutation queue serializes authoritative game mutations.
- Accepted move updates RAM, persists one chess game document, then broadcasts/ACKs authoritative state.
- If persistence fails, runtime game/chess.js state is rolled back from the pre-mutation snapshot.
- recentRequestIds is persisted (bounded to 24) for duplicate command protection across restart.
- revision is monotonic and client move commands include expectedRevision.
- Client applies successful mutation ACK state, so a lost broadcast does not leave the local revision stale.
- Invite acceptance stores its requestId in the created game, allowing the same accept retry to resolve the already-created game after a lost ACK.
- Active-user locks for both players are created atomically with game creation and removed when the game finishes.
- Active locks are not refreshed on every move.

5) FIRESTORE IMPACT
New collection:
- families/{familyId}/chessGames/{gameId}
  Durable game metadata, FEN, PGN, clocks snapshot, result, history, revision and request IDs.
New server-only root collection:
- chessActiveUsers/{uid}
  { uid, familyId, gameId, createdAt }
Rules:
- family member + player may get own game rows.
- history list also requires request.query.limit <= 20.
- mobile create/update/delete chessGames: DENIED.
- mobile read/write chessActiveUsers: DENIED.
Index:
- chessGames: playerUids ARRAY_CONTAINS + status ASC + endedAt DESC.
No data migration/backfill.

6) FIRESTORE COST DISCIPLINE
- No Firestore timer ticks.
- No Firestore heartbeat/presence.
- No Firestore Socket transport.
- Accepted normal move: one chessGames document persistence operation.
- Game creation additionally creates two server-only active UID lock documents transactionally.
- Finish writes final game state and deletes the two active UID locks in one batch.
- History is one-shot, latest 20, load-more pagination; no onSnapshot history listener.
- Chess Lobby reuses existing FamilyRealtimeContext family.members cache; no extra family member listener.

7) PRESENCE / FAMILY ISOLATION
- Presence is Socket RAM only.
- Same-family game sockets remain visible as in_game after leaving the lobby.
- If a UID has an active game in another family, a different-family lobby does not expose that game as in_game; the user is not challenge-ready.
- Invite delivery/join uses sockets already scoped to the matching family/game context, avoiding stale automatic joins across family switches.
