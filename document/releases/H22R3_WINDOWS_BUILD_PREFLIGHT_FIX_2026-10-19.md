# Family Bloom H22R3 — Windows Build & Share / AAPT2 preflight repair

Date: 2026-10-19  |  Base: H22R2 FULL CODE  |  Native identity **unchanged**: `1.3.22`, `versionCode 143032`, `P2.37R2C-H22-native-1`.

## Reported failure and confirmed reason

During `Family_Bloom_BUILD_APK_TO_SHARE.bat`, before Gradle runs, `scripts/test-phase-p2_37r2c_h21r3-android-aapt-audio.cjs` line 41 raised:

`AssertionError [ERR_ASSERTION]: assert(idxStage>0 && idxValidate>idxStage && idxGradle>idxValidate)`

The previous test searched for the literal `check-android-resource-names.js\r\n` in a checked-in BAT that used `\n` line endings. The release BAT **actually staged audio, validated AAPT2 resources, then assembled Release** in the correct order. The failure was a false-positive test assertion and stopped the build before compiling anything.

Additionally, a separate existing structural audit `scripts/setup/check-build-entrypoints.js` would have failed later: seven shipped BAT files had bare LF instead of required Windows CRLF. The H21R6 strict server typecheck BAT was also shipped but absent from the canonical BAT manifest.

## Corrections implemented

1. Harden `scripts/test-phase-p2_37r2c_h21r3-android-aapt-audio.cjs` to parse active BAT commands, normalize LF/CRLF, and validate the actual ordering `source-only resource check -> Expo prebuild -> audio staging -> full resource validation -> Gradle assembleRelease`. The test deliberately mutates the BAT to verify removal of either gate or an early Gradle command still fails. This **does not bypass** AAPT2 validation.
2. Normalize the 7 affected BAT files to native Windows CRLF: two under `scripts/android/build`, one EAS, one install, one CLEAN APPLY maintenance, two verify files.
3. Add `scripts/android/maintenance/Family_Bloom_VERIFY_SERVER_TYPES.bat` to `scripts/setup/bat-entrypoints-manifest.json`. The canonical manifest now tracks all **33** shipped BAT files.
4. Introduce `scripts/test-h22r3-windows-build-preflight.cjs` as a cross-platform, dependency-free Windows packaging gate. It checks the 33 canonical BATs, audit integration, resource staging order, release delegation, and the relevant script invocation. Run this early in: Build & Share, direct Android Release, CLEAN APPLY and EAS Build.
5. Update only human-readable build identifiers in the Build & Share and CLEAN APPLY BATs to H22R3. Preserve Chess H21R6, Xiangqi H22, Bot countdown H22R1, H22R2 cleanup protection, server protocol, Android native source/assets/version codes, APK SHA-256 publication checks and stable copy-over BAT entrypoints.

## Updating an H22R2 project

1. Make a backup. Unzip the H22R3 FULL CODE archive into a **new separate folder**.
2. Run the **H22R3** `Family_Bloom_PRE_COPY_CLEAN_OLD_PROJECT.bat` and point it at the existing project when prompted. Do not run an older BAT.
3. Copy the complete H22R3 source tree onto the existing project, replacing all files; keep the `document/` directory intact.
4. In the updated project run `Family_Bloom_CLEAN_APPLY_FULL.bat`, then `Family_Bloom_BUILD_APK_TO_SHARE.bat`.
5. For immediate isolated verification before building: `node scripts/test-h22r3-windows-build-preflight.cjs` and `node scripts/test-phase-p2_37r2c_h21r3-android-aapt-audio.cjs` should both PASS.
6. Distribute only the APK generated by the new successful build. A previous `Family_Bloom_LATEST.apk` is not evidence that the failed H22R2 build succeeded.

No Render redeployment is required for this H22R3 build-script-only change. If H22 server was not deployed, it still must be deployed for Xiangqi gameplay independently.
